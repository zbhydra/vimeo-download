# 正式环境解析与下载失败修复方案

日期：2026-10-19。状态：方案已批准，R1 修复已冻结，待原 reviewer 定向复验；首轮记录见 §8，审查问题与修复见 §9。

本方案基于 `bb11449` 源码、[原始调研](2026-10-19-正式环境解析与下载失败调研.md)、生产库只读查询、生产日志与 `nginx -T`，并由 herdr 中的主协调器、Opus 5.5 max、ccmp 分别调研和交叉审查。生产数据窗口截止 2026-10-19 03:21 UTC。

## 1. 建议与实施顺序

先修解析与材料合同，再替换网页存储实现，最后依据修正后的数据治理代理。保留现有「一次解析选择一个节点和代理、材料自包含、失败后用户重试」的产品模型。

| 批次 | 改动 | 可独立验收的结果 |
| --- | --- | --- |
| A：解析与材料 | hash 归一、resource token 压缩与签发上限、失败分类、超时预算、下载 start 埋点 | 有效 unlisted 链接带完整访问参数；不再签发因体积必然被下载入口拒绝的 token；失败返回可读业务错误；开始次数不再依赖下载成功 |
| B：网页存储 | 统一 Worker OPFS 写入，接通预检、临时文件和 direct 恢复写入 | Safari 17/18 在支持的业务大小范围内可下载大文件；合并输出支持随机写；恢复记录与文件提交顺序一致 |
| C：代理验证 | 对修复后仍失败的相同链接比较现有出口与候选出口 | 区分链接权限与出口可用性，取得证据后决定代理调整 |

## 2. 本轮复核后的事实

### 2.1 统计口径

原报告的事件总量成立：解析成功 29、失败 47；下载成功 16、失败 8、预检拦截 2；下载 start 16。

47 条解析失败按打点 `reason` 的互斥分布如下，不能再与服务端状态计数相加：

| reason | 条数 | 能证明什么 |
| --- | --- | --- |
| `NETWORK_ERROR` | 28 | 浏览器未取得可消费的响应；不能直接认定为代理拦截 |
| `24034` | 9 | 解析节点返回不可用；具体原因仍看同次请求诊断 |
| `24050` | 2 | 无可用解析代理 |
| `24033` | 2 | 当前映射为资源不存在或不可达，包括不支持的 Vimeo 路径形态 |
| `24031` | 5 | 不支持的平台 |
| `REQUEST_TIMEOUT` | 1 | 解析预授权在客户端超时 |

- 失败设备为 **34** 个，47 条失败记录的 `user_id` 均为空。不能从「每设备只有一次失败」推出首次使用失败或随后流失。
- 带路径 hash 的失败为 **12** 条，其中 9 条是 `NETWORK_ERROR`、3 条是 `24034`；URL 形态只能标记受影响候选，不能证明改完都会成功。
- 下载 8 条失败包括：HTTP 422 三条、预授权 10 秒超时两条、轨道 fetch/读流失败两条、`QuotaExceededError` 一条。后两类不能仅凭日志分别断言 CDN 主动断流或用户磁盘不足。
- 两条 Safari 预检拦截都为 `client_mux`，文件大小分别为 2,277,269,984 字节和 89,065,941 字节，UA 分别为 Safari 18.7.5、17.6，底层错误都是缺少 `createWritable()`。

### 2.2 时间与超时

- `mark_time` 是毫秒时间戳；`app.log` 原文是 `America/New_York`，本窗口为 UTC−4。可对账样例：`log_id=48` 的 UTC 07:19:12 对应 app.log 03:19:11。不能把日志原文当 UTC，也不能仅按视频 ID 合并不同请求。
- 按纽约时间转 UTC 后，同窗口有 86 次 `parse-v2` 请求，45 次耗时至少 59 秒。这是请求量，包含未对应客户端失败打点的请求，不能与 47 条失败逐条等同。
- 生产磁盘配置经 `nginx -T` 确认：全局请求体上限为 `50m`；全局与 Vimeo API server 块均未显式设置读写超时。nginx 官方默认读超时为 60 秒。
- Provider 预算为 60 秒，浏览器节点预算为 70 秒，存在错误响应与反向代理超时竞争的设计问题；尚未取得单次请求的 nginx 504/连接断开证据，不能把所有 `NETWORK_ERROR` 都归到该竞争。

## 3. 批次 A：修复解析与材料合同

### 3.1 在 canonical 层归一访问 hash

由 `VimeoMedia._compute_canonical_link` 把标准 `/<id>/<10 位十六进制 hash>` 归一为 `/<id>?h=<hash>`，继续保留受支持的其他 query 参数。query 已有 `h` 时以 query 为准。`player.vimeo.com/video/<id>?h=...` 仍归一到同一身份。

归一发生在视频 ID 提取之前，避免全数字 hash 被误当成视频 ID。只识别标准两段路径，不把 channel 等多段路径的数字误认成访问 hash。`_player_page_url` 继续消费 canonical 的 query。

同一资源的两种 URL 写法将得到相同排重键。匿名排重和登录 6 小时免扣算法继续使用既有资源键，不引入旧键迁移或双查。路径形式发生归一的旧缓存可能不再命中原排重键，发布时需说明此边界。

### 3.2 只压缩 resource token，统一签发与接收上限

保留自包含材料，不引入 Redis/数据库材料引用。

1. resource payload 序列化后用标准库 zlib 压缩，再将二进制结果直接交给 Fernet；不额外套 base64 或 JSON 压缩信封。解码先 Fernet 认证，再解压和校验原有 claims/material。
2. proxy execution token 的编码、TTL 和两类 token 共用的 claims 版本保持不变。
3. 资源 token 上限先保留 **1 MiB**，在现有常量模块中统一所有引用；签发后检查最终编码长度，超限就在解析阶段返回现有 `24032`，引导插件，不把必然在下载入口失败的材料发给用户。
4. HTTP schema、业务预授权与 token 解码使用同一体积合同；内部不再维护独立硬编码。保留实际入口所需的类型、非空和材料认证校验。
5. 新解码器只接收新的压缩 resource 格式，旧格式返回现有 `24053`。无效材料发生在匿名计次和登录扣费之前，不消耗新额度。旧页面或解析快照需要重新解析；不增加长期兼容分支。

原报告的 850 MB 样例显示，完整分片清单导致约 246 万字符的 token，压缩后约 31 万字符；本轮未重新生成此材料。实施验收必须重跑该真实样例，并核查另外两条 422 对应的资源，不能仅凭同为 422 宣布全部修复。

1 MiB 不保证覆盖任意时长或分片数的 4 GiB 视频；4 GiB 是媒体大小上限。压缩后仍超限的资源明确转插件。客户端解析快照仍按自身容量预算尽力保存，不为大 token 放宽 localStorage 上限。

### 3.3 输入和解析失败尽早结束

解析预授权完成 URL 基础校验后，复用既有平台识别，在申请节点和代理前拒绝不支持的平台，避免非 Vimeo 输入进入代理准备链路。复用现有错误映射语义，将底层平台不支持的 `24000` 转为 V2 的 `24031`；解析执行入口仍校验其必要合同。

Provider 保留正常播放器页面的 inline/XHR 配置捕获路径，补上明确错误页面的退出条件。已取得当前视频的有效配置时以配置为准；挑战 frame 仅记录为诊断线索，不能单独触发失败或覆盖成功结果：

| 证据 | 行为 |
| --- | --- |
| 未取得有效配置，且播放器页面有 `cf-mitigated: challenge` 或既有挑战 DOM | 返回节点暂不可用，不再等待播放器配置 |
| HTTP 404 | 返回资源不存在/不可达 |
| HTTP 401/403 且无明确挑战证据 | 返回当前无法访问，提示检查完整链接与访问权限；不断言视频已删除或代理一定被封 |
| HTTP 429、上游 5xx | 返回节点/上游暂不可用 |
| 成功页面尚未取得配置 | 继续等待当前视频配置，受总预算限制 |

复用既有错误码及诊断字段；401/403 复用包含「不可达」映射的 `24033`，同步后端全部 locale，准确表达「不存在或当前无法访问」。已有 `#challenge-stage` 检测继续保留，不把它列为新功能。

Provider 处理预算改为 **50 秒**，nginx 明确设置读写预算 **65 秒**，浏览器节点预算保持 **70 秒**。正常返回前预留清理和传输余量；这是预算安排，不承诺所有失败都能在 2–5 秒发现。

部署测试按当前 API 合同修订：移除旧媒体转发、Range 转发、关闭媒体缓冲和 3600 秒等已失效断言，检查本轮所需的 API 超时与 CORS 配置。

### 3.4 修复下载 start 口径

- `start` 表示本轮合法下载执行被提交给下载器；新下载在存储预检通过后、申请授权前记录，继续下载在恢复记录校验后记录。
- 在 `runSingleResourcePlan` 的公共执行点前移记录，覆盖现有调用方，删除成功后的补记。实际节点信息可继续更新，不再决定 start 是否发生。
- `success` 表示文件已生成并触发浏览器保存，不代表用户已将文件保存到磁盘。
- 匿名等待取消、转插件、页面离开可能没有终态，允许 `start` 大于成功与失败之和。失败率仍使用 `failed / (success + failed)`，预检阻断单列。
- 当前唯一 Provider 每次只返回一个资源，本轮不扩展多资源批量能力，也不构造不可达批量场景作为验收。

## 4. 批次 B：统一网页 OPFS 写入

### 4.1 选择 Dedicated Worker + SyncAccessHandle

统一使用 Worker 中的 `createSyncAccessHandle()` 写 OPFS，替换主线程 `createWritable()` 的四处实现：预检、client_mux 临时文件、direct 初始文件、direct 恢复写入。主线程继续读取 File 和删除目录项。

该选择让各下载路径使用同一磁盘写入合同，支持 mux 输出按位置回填和 direct 从 checkpoint 偏移继续写。IndexedDB 继续保存轻量恢复记录；不另建分片数据库、读写适配层或整文件内存兜底。

能力检测继续依据实际写入、关闭、读取、删除结果，UA 只用于诊断。内存 50/100 MiB 上限和容量门禁保持：client_mux 为双轨加输出预留约两倍成品空间，direct 按单文件预留。

### 4.2 必须统一的文件语义

- Worker 支持现有的顺序写和按位置写；同一实际写操作只保留一个接口，不分别维护顺序写与随机写两套存储逻辑。按 `write()` 实际返回的字节数确认完成，未写完不能推进已完成偏移。多份临时文件复用写入运行时，不为每个分片创建 Worker。
- SyncAccessHandle 是原地写入，不把 `abort` 描述为事务回滚。正常完成按 `flush → close → getFile` 执行；失败时即使 flush 失败也须释放句柄，再删除本轮临时文件。读取 File 和删除前都必须释放写入锁。
- direct 按 `write → flush → 保存 checkpoint` 执行，沿用已有 1 MiB/1 秒的 checkpoint 节流。恢复时，文件短于 checkpoint 则记录失效；文件领先 checkpoint 时截断未确认尾部，再从**记录中的已确认偏移**继续，不能以实际文件大小跳过未确认数据。
- Worker 传回错误时保留错误名；配额不足走既有存储错误和本地化提示，不把浏览器英文异常或 Worker 协议文本直接给用户。
- 延迟保存所需的输出 File 保留到现有清理时点；受控成功、失败、重试路径关闭句柄和清理临时资源，清理需容忍句柄已关闭。浏览器被杀死后的孤儿文件清理不在本轮保证内，不为此新增租约或后台协调。

### 4.3 覆盖边界

MDN 兼容数据表明：Safari 26 才加入 `createWritable`，`createSyncAccessHandle` 从 Safari 15.2 提供，部分同步方法语义从 16.4 完整统一。首轮验收面向报告中的 Safari 17.6、18.7.5，不宣称已验证 Safari 15/16。

统一 Worker 会改变 Chrome 86–101 的大文件能力，因为这些版本有异步写 API、没有 SyncAccessHandle。验收基线为 Chrome/Edge 102+、Firefox 111+、Safari 17+，最终以真实能力探测为准；基线以下继续按既有小文件内存规则或插件引导处理。Playwright WebKit 只能提供补充验证，不能替代指定 Safari 版本的实机结果。

## 6. 发布与效果判断

批次 A 的业务入口和解析节点作为同一发布批次连续更新；不混用新旧 resource 编码做长期运行。切换窗口允许明确失败，旧材料在完整更新后通过重新解析修正，proxy token 不受编码变化影响。

批次 B 在 Safari 实机与 Chromium 回归均通过后单独发布。仍保留业务大小门禁、浏览器配额限制和真实网络失败，不将 OPFS 适配描述为所有大文件必然成功。

上线后的判断指标为：可访问 hash 样例成功、有效 token 不再因本项目体积合同产生 422、错误页不再挂满总预算、Safari 支持范围内能完成真实文件、start 与执行顺序一致。按这些行为验收，不承诺从历史样本直接减少某个固定条数。

代理验证放在代码缺陷修复之后：使用相同公开链接、有效 hash 链接和受阻链接，对照候选出口的成功与失败。只有确认出口差异后才调整代理，不增加自动换代理、后台重试或账号 Cookie 池。
