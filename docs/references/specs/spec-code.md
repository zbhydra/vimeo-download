# 通用编码规范（注释 / 错误消息 / 简化技巧）

> 与语言无关的**强制规范**，写 / 改任何代码前必读。
> 语言专属细则见 [[spec-python]]、[[spec-extension]]、[[spec-website]]；判断优先级链见根 `AGENTS.md` §2。

## 1. 注释

**总原则：解释「为何」，不解释「何为」。** 代码首先是写给人类阅读和维护的。

必须写：

- **文件头**：每个文件顶部说明这个文件是干什么的。包含复杂流程的，列出流程图。
- **公开 API 文档字符串**：所有公开函数、类、模块，说明用途、参数、返回值。
- **函数参数**：非自解释的参数说明其含义与取值约束。
- **非直观业务规则**：复杂逻辑或业务规则背后的**原理**，不是它的字面行为。
- **复杂算法**：逐步内联注释拆解，提升可维护性。
- **有争议的写法**：为什么这样做、为什么不用看起来更自然的那种写法。
- **技术债**：所有权宜方案 / 临时方案标注 `TODO:` 或 `FIXME:`，并写明采用捷径的原因。

不要写：

- 显而易见的代码的复述（`i++ // i 加一`）。
- 自解释字段的注释（`userId: string // 用户 ID`）。
- `type` / `interface` 字段与 `const` 的注释按此标准判断：**写业务含义、单位、取值范围、边界语义**，纯重复字段名的不写。

> 「详细注释」指的是信息密度高，不是数量多。一条解释清楚「为何」的注释，胜过十条复述「何为」的。

## 2. 错误消息

抛出的错误必须**可定位**，拒绝泛化错误。

**禁止**：

```
throw new Error('Failed to start local WhatsApp runtime')
```

错在：不知道哪一步失败、不知道失败的具体对象、不知道底层原因。

**必须包含**：

1. **哪里**——哪个模块 / 哪个函数 / 处理哪个对象（带 ID）。
2. **什么错**——具体失败的是什么，不是笼统的「失败了」。
3. **上下文**——如果是请求：哪个接口、返回什么内容、什么状态码、是解析错误还是网络错误。

**即使已经 `catch` 了错误，也要 `console.error(error)` 打印原始错误对象**，保留堆栈方便调试。

## 3. 保持简洁

- 未经允许不新增依赖、不新增功能 / 组件（根 `AGENTS.md` §3 红线 5）。
- 实现新方案后删干净被替代的旧方案与备用分支残留（红线 6）。
- 内部操作不做过度防御性编程——外部输入才需要校验，内部调用信任调用方。

## 4. 简化设计技巧

- **无限期用超长有限期表达**：需要「永不过期」时存一个 200 年后的时间戳，就能只用一个 `int` 字段和一套统一的过期判断逻辑，不需要 `null` 分支或额外的 `is_permanent` 标志位。
