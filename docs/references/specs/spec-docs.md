# 文档规范（feat / tech / plans）

> `docs/` 下产品与技术文档的**强制规范**，写 / 改 docs 前必读。
> 目录总览见根 `AGENTS.md` §4。

## 1. 目录结构

```
docs/feat/
  000.架构/              # 地基域：跨业务共享的技术基础（非产品功能）
    overview.md          # 各端职责 / 技术栈 / 数据流 / 域依赖地图（地基域用 overview，不用 feat.md）
    tech-*.md            # 一个域可有多份，按子主题拆分
    references/          # 源 feat 索引、引用资源
    plans/               # 执行文档
    changelog.md
  0NN.<业务域>/          # 业务域：产品功能；NN 为两位序号，域内结构同 000
    feat.md              # 产品需求
    tech-*.md            # 技术实现
    references/
    plans/
    changelog.md
  archive/               # 已废弃的源 feat（历史快照，不进活文档库）

docs/ops/
  <日期>-<范围>.md       # 按次发布单，执行完成后移入 archive/ 并在对应域 changelog 回填发布事实
```

**当前业务域**（以 `docs/feat/` 实际目录为准，本文不维护完整清单）：`002.下载功能`、`003.积分系统`、`004.订单系统`、`005.计数器系统`、`006.订阅系统`、`007.用户系统`、`008.管理后台`、`009.SEO与增长`、`010.多语言`、`011.Pricing页`。新增域时按 `0NN.<域>` 命名并在本段补一行。

## 2. feat.md：产品需求

**严格无代码**——不出现 API 路径、表字段、类名、错误码。

必备内容：

- 功能目标
- 功能范围：包含哪些、不包含哪些（划定边界）
- 业务流程：主流程、异常流程（如支付失败）、分支流程
- 非功能性需求：性能（如页面加载 < 1 秒）、安全性、兼容性
- 验收标准
- 数据埋点：需要收集哪些用户行为数据
- 该功能的**所有**设置项与界面元素
- 用户的操作逻辑

**每一个界面元素都必须有说明**：这是什么元素、以什么形式存在、是否可点击、点击后如何、宽高多少、有什么动画、有无图标。

同一件事只在一个地方说明，其他地方用引用指向。

## 3. tech-*.md：技术实现

一个 feat 可能很大，技术文档按子主题拆分。例：`tech-登录-google.md` / `tech-登录-github.md` / `tech-登录-email.md`。

**定位**：记录架构、边界、合同、流程、取舍和验收口径，**不是源码的副本**。

**禁止**放入可直接复制到项目的详细实现代码——包括完整函数、类、组件、import 和语言特定的控制流。表达逻辑优先用流程图、决策表和文字；必须用代码块时**最多只能写语言无关的伪代码**。

API 请求 / 响应、数据结构、配置和 schema 可保留必要的**合同示例**，但必须最小化，且不含实现逻辑。

必备内容：

- 新建 / 修改 / 删除的文件树
- 接口定义（API Spec）：请求方法、参数名称与类型、是否必传、返回值结构、错误码
- 数据规格：表结构、字段类型、长度、默认值、索引
- 算法 / 逻辑细节：计算公式、排序规则、超时处理
- UI 规格：尺寸、颜色、字号、间距、状态（按压 / 悬停 / 禁用）
- 交互规格：动画时长、缓动函数、滚动边界响应

## 4. plans/：执行文档

- 一个任务跟踪清单 + 验收记录。
- 命名：`001.xxxxxxxxx.md`
- **这个文档后续可能被删除**，所以不要放：重要决策（应同步回 feat / tech）、备忘、重要技术路线（可以放细节，但正式结论要落回 tech）。
- 复杂任务要仔细思考如何分阶段，每个阶段**可验收**、**可并行**。
