# 索引规则

## 经过主要条件（例如 user_id）过滤后，数据还有多少？
- 非常多，应当加
- 非常少，不应当继续加

## 加索引前的思考
- 这个索引是业务频繁使用的吗？
  - 是主要的业务，查询频率非常高 - 应该加
  - 不是，很少查询，后台查询 - 非常低
- 什么时候加>=3个联合索引
  - 业务查询真的非常频繁，已经到了不得不加的情况了
  - 只是一个后台运营查询 - 绝不能加。如果运营这类可延迟的查询，数据量又巨大无比，考虑的是定时任务聚合而不是加索引

**加/改索引前必须在 PR 里贴三样，缺一拒绝**：
1. 本表现有 PK/UK/INDEX 清单 —— 证明不是已有索引的最左前缀重复。
2. grep 出来的实际查询代码位置（文件:行号 + WHERE/ORDER BY）—— 必须是当前代码已在查，不是"以后会查"。
3. 索引行尾 `#` 注释写明服务哪个查询。

**硬禁令**：
- 没有实际查询的索引 —— 不加。
- 联合索引最左前缀能覆盖的单列索引 —— 删掉。
- `unique=True` 列上再加普通索引 —— 删掉。
- 主键列放进联合索引末尾 —— 删掉（PK 已隐含）。
- 低基数列（status/bool/≤10 枚举）单列索引 —— 不加。
- `LIKE '%x%'` / `LIKE '%x'` 列加 B-tree —— 不加。
- 索引名列顺序与定义不一致 —— 改名。

**加联合索引时，必须回审同表单列索引是否要一起删。**
