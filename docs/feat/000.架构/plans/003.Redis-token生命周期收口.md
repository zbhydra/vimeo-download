# 003 · Redis token 生命周期收口

> 状态：阶段一至三已完成；阶段四生产清理待人工确认与执行

## 目标

让用户与管理员 token ZSet 随 JWT 自身过期时间自动回收，阻止不再访问的账号永久留下 Redis key；在不改变登录、续签、登出、插件换 token 与管理员认证行为的前提下，清理已有无 TTL token key，并保证更新前签发的有效 token 无缝延续到自身 JWT `exp`。

## 证据

- `UserTokenService.store_token()` 与 `AdminTokenService.store_refresh_token()` 只执行 `ZADD`，把 JWT `exp` 写入 score，但不给当前 token ZSet 设置 key TTL。
- 两个 service 仅在再次验证某个 token 时惰性删除该成员；用户不再访问后，过期成员与空闲 key 没有回收入口。
- 用户登录、用户 refresh、Website 向 Extension 换 token、管理员登录和管理员 refresh 均可达上述写入路径。
- 生产只读检查确认 access / refresh token key 是当前 Redis keyspace 的主要组成部分；具体数量属于运行态，不写入长期技术合同。

## 范围

### 包含

- 用户 access / refresh token ZSet 写入与 refresh 轮换时同步设置 key TTL。
- 管理员 refresh token ZSet 写入与轮换时同步设置 key TTL。
- 一次性历史清理脚本：扫描现有 token key，按 ZSet 最大 score 为无 TTL key 补过期时间。
- 用户与管理员 token 生命周期的真实 Redis 测试。
- 旧无 TTL token key 与旧客户端的无缝回归验收。
- Redis 通用 TTL / transaction pipeline 规范、后端测试目录规范、用户认证技术合同、管理员认证技术合同与实施 changelog 同步。

### 不包含

- 不修改 JWT 格式、摘要算法、有效期配置、Redis key 名或 refresh 宽限期。
- 不修改登录、续签、登出、插件换 token、管理员认证 API 及响应。
- 不要求 Website、Extension、Extension Pro 或 Admin 前端随本次后端发布升级。
- 不新增 Lua、锁、CAS、重试、后台任务、定时清理或共享 Redis helper。
- 不调整 Redis `maxmemory`、淘汰策略、连接池或部署配置。
- 不处理 device trust、额度、限流、缓存、锁与 Redis Stream。
- 不追求多进程写入时以所有成员最大 score 作为日常 key TTL；并发写入以最后完成的 `EXPIREAT` 为准。

## 生命周期合同

### 当前 token ZSet

用户 access、用户 refresh、管理员 refresh 继续使用现有结构：

- key：现有账号维度 key，不改名；
- member：token 摘要；
- score：JWT `exp`，Unix 秒；
- key TTL：最近一次成功写入 token 的 `expires_at`。

同一个 key 只存同一 token 类型，新签发 token 的绝对 `expires_at` 不早于已有成员 score（大于或等于）。同秒签发可得到相等 `expires_at`；该顺序是调用方合同，不增加运行时扫描或校验。token 有效期配置只能保持或延长；若缩短配置，新的 `EXPIREAT` 会使同 key 中按旧周期签发的 token 提前失效。

每次新增当前 token 时，使用 Redis transaction pipeline 顺序执行：

1. `ZADD` 新 token 摘要与 `expires_at`；
2. `EXPIREAT key expires_at`。

`ZADD` 与 `EXPIREAT` 必须在同一个 transaction pipeline 中提交，避免创建出永久 key。pipeline 成功后，单独执行 `ZREMRANGEBYSCORE key -inf now` 删除已经过期的旧成员。该清理使用 Redis 的 score 范围操作，不把成员加载到应用层，也不与写入组成原子事务。

当前 token 注册表写入属于正确性优先的 fail-closed 依赖。transaction pipeline 异常由对应 token service 记录原始堆栈后重新抛出，不新增重试、兜底或错误码。过期成员清理只控制活跃 ZSet 的内存增长；清理异常记录原始堆栈后忽略，不改变已经成功的登录或续签结果。

并发写入若让较早的 `EXPIREAT` 最后完成，允许同账号其他 token 在极窄窗口内早于自身 JWT `exp` 失效；用户重新登录或刷新即可恢复，不为此增加最大 score 计算或并发控制。

### refresh 宽限期 ZSet

`refresh_token_old` 与 `admin_refresh_token_old` 保持现有独立短 TTL。轮换 pipeline 只需为当前 refresh ZSet 增加 `EXPIREAT new_expires_at`，不改变旧 token 宽限期流程。

### 验证与撤销

- `verify_token`、当前 refresh 验证和宽限期验证保持现有 score 判断与惰性撤销语义。
- `revoke_token`、批量撤销和 best-effort 旧插件 token 撤销保持现有行为。
- key 到期后缺失与 token 被撤销同义，继续返回认证失败。
- key、member、score 与 JWT 均不变；更新前创建的无 TTL key 继续按原路径读取，有效旧 token 无需重新签发或刷新。

Redis 官方合同：

- [`EXPIREAT`](https://redis.io/docs/latest/commands/expireat/) 使用 Unix 秒设置 key 绝对过期时间。
- [`ZREMRANGEBYSCORE`](https://redis.io/docs/latest/commands/zremrangebyscore/) 按 score 范围删除成员，不需要把 ZSet 全量读到应用层。
- [`MULTI` / `EXEC`](https://redis.io/docs/latest/develop/using-commands/transactions/) 保证事务中的命令串行、隔离执行；redis-py transaction pipeline 复用该合同。

## 历史清理

新增一次性 CLI 脚本，默认 dry-run，显式 `--execute` 才修改 Redis。生产 CLI 从 `settings.redis.key_prefix` 取得完整命名空间，扫描该命名空间下用户 access / refresh 与管理员 refresh pattern。pattern 也可能命中名称含 `_old` 的宽限期 key；脚本通过“已有 TTL 直接跳过”保证不处理宽限期 key，而不是依赖 pattern 隔离。

脚本使用 [`SCAN`](https://redis.io/docs/latest/commands/scan/) 增量遍历，不使用阻塞全库的 `KEYS`。按有界批次执行：

1. 读取 key 当前过期状态，并用 `ZRANGE key -1 -1 WITHSCORES` 读取最大 score；该操作利用 ZSet 有序结构，不遍历全部成员；返回空表示 key 已不存在或已无成员，直接跳过；
2. dry-run 只累计并输出扫描 key、无 TTL key、最大 score 已过期 key、最大 score 仍有效 key 数；
3. execute 只对当前没有 TTL 的 key 执行 `EXPIREAT key max_score NX`；已有 TTL 不覆盖；
4. 最大 score 已过期时，Redis 会因设置过去时间而删除整个 key；最大 score 仍有效时，key 在最后一个 token 到期时自动删除。

脚本不记录 key、用户 ID、token 摘要或成员内容。`ZRANGE` 返回空属于正常并发删除，直接跳过；其他中途失败报错退出。已处理数据符合最终合同，重新执行即可继续收口，不增加进度状态、恢复游标或后台补偿。

清理 runner 显式接收完整 key 前缀作为扫描边界；CLI main 固定传入运行配置前缀，不开放任意生产前缀参数。真实测试传入含 `test_run_id` 的独立子前缀，只能扫描、修改和删除本测试命名空间。历史清理不单独增删或改写 member / score；最大 score 已过期时只通过 key 到期删除全部已过期成员。与并发 token 签发冲突时，`NX` 保留应用已经设置的 TTL。

发布顺序固定为：先部署新写入合同，再 dry-run 历史清理，确认统计后 execute。历史清理不单独增删或改写 member / score；最大 score 仍有效的旧 key 只补过期时间，因此有效旧 token、旧客户端与现有认证接口无感。

## 阶段与验收

### 阶段一：当前写入生命周期

实现用户与管理员 token service 的 transaction pipeline，不改调用方。

验收：

- 新建用户 access / refresh 与管理员 refresh ZSet 时同时存在绝对过期时间。
- refresh 轮换后当前 ZSet 的 TTL 对齐新 refresh token `exp`，宽限期 key 仍按现有短 TTL 回收。
- transaction pipeline 成功后删除当前 ZSet 中 `score <= now` 的成员，新写入 token 保留。
- 登录、刷新、登出、插件换 token 与管理员刷新接口合同不变。
- 更新前签发的有效用户、插件与管理员 token 在更新后继续校验成功，不要求重新登录或客户端升级。
- Redis 写入 transaction 失败按 fail-closed 记录原始堆栈并重新抛出，不新增重试或兜底。
- transaction 成功后的过期成员清理失败只记录原始堆栈，登录与刷新仍按成功返回。

### 阶段二：历史清理工具

实现一次性脚本及 dry-run 统计，不接入应用 lifespan、cron 或部署脚本自动执行。

验收：

- dry-run 不修改 key、成员或 TTL。
- execute 不单独增删或改写 member / score；没有 TTL 的 key 按最大 score 补 TTL，已有 TTL 不覆盖。
- 最大 score 已过期的 ZSet 通过 `EXPIREAT` 删除，最大 score 仍有效的 ZSet 保留到该时间。
- `SCAN` 后 key 被并发撤销或到期、导致 `ZRANGE` 返回空时直接跳过，不报错、不重试。
- 重复执行结果稳定，不依赖上次运行游标。
- 输出不包含 key、用户 ID 或 token 摘要。
- 与应用并发签发 token 时，清理不会覆盖应用已设置的 TTL，也不显式删除 key。
- 清理最大 score 仍有效的旧 key 前后，所有 member、score 与有效旧 token 校验结果保持不变。

### 阶段三：真实测试与文档同步

验收：

- 真实 Redis 按源码镜像拆分，覆盖用户 access / refresh、写入后过期成员清理、用户 refresh 轮换、管理员 refresh、旧无 TTL key、历史清理读取前 key 已消失、dry-run、execute 与重复执行。
- service 测试使用独立 key 并在 teardown 删除；清理测试向 runner 传入含 `test_run_id` 的独立前缀，断言前缀外哨兵 key 的成员与 TTL 均未改变。
- 兼容回归先直接创建没有 TTL 的旧结构 ZSet，再用新 service 验证有效 token、完成 refresh 轮换并执行清理；全过程不重新签发被验证的旧 token。
- 通用规范与两个认证域技术合同描述一致，旧“仅惰性撤销、无 key TTL”表述全部删除。

## 已知限制与风险接受

- transaction pipeline 只保证同次写入不会创建永久 key，不解决多进程覆盖 TTL；接受极窄并发窗口内某个同账号 token 提前失效。
- 日常写入依赖“新 token 的绝对 `expires_at` 不早于同 key 已有 score（大于或等于）”合同；不扫描成员验证该条件。
- token 有效期配置不得直接缩短；缩短后新 token 的绝对过期时间可能早于存量 score，`EXPIREAT` 会使该 key 中部分存量 token 提前失效，用户需重新登录。
- 日常过期成员清理与写入不原子；新 token 的 score 晚于 `now`，不会被范围删除。清理失败仅延迟内存回收，key TTL 仍保证最终整体删除。
- 历史清理只读取最大 score；score 继续以现有 JWT `exp` Unix 秒为唯一事实，不引入第二套过期配置。
- Redis `allkeys-lru` 仍可能在达到内存上限时淘汰有效 token，本计划不修改淘汰策略；生命周期收口用于避免无期限增长，不提供持久会话保证。
- 生产历史清理是可恢复的局部操作：单批失败不回滚已处理 key，重新执行即可。
