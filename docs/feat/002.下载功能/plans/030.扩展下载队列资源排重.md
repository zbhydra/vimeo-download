# 030. 扩展下载队列资源排重

> **部分作废**：本计划成文于多平台时期。Instagram / X / Telegram / Threads 站点与 `website-tgd-pro`、`extension-pro` 已随单平台（Vimeo）转型整体删除，文中这些平台与站点的条目只作历史记录；现行架构以 `../tech-站点适配.md` 与 `../references/index.md` 为准。
> 状态：待批准；本次仅获准基于已完成的 Plan 029 修订计划基线，生产代码仍未获准实施。Plan 029 已在 HEAD `683c2fe7` 完成共享队列取消语义；本文只负责资源身份与入队排重，不修改取消合同。

## 1. 背景与证据

当前 extension 的所有页面按钮与 Popup 最终都调用 `downloadOne`、`downloadMany` 或 `enqueueMany`，并进入当前 content document 唯一的 `DownloadManager.enqueue`。Manager 已保证逻辑 FIFO 单活动任务，但每次 enqueue 都无条件创建新 task；同一资源从批内重复项、页面重复点击或不同入口再次提交时，会分别进入队列、扣额并下载。

现有源码与合同明确保留了该行为：

- `extension/src/core/content/download/downloadManager.ts` 的 `enqueue` 对输入逐项调用 `createTask`，没有查询现有任务。
- `extension/src/core/content/download/download.ts` 声明重复项会重复扣额并下载。
- `extension/tests/unit/download-many.spec.ts` 和 `download-queue.spec.ts` 分别锁定重复执行与重复 task 行。
- `@../tech-扩展端Instagram本地下载.md`、`@../tech-站点适配.md` 和历史 Plan 015 明确记录重复点击独立执行。

排重不能直接建立在现有 raw `MediaResource.id` 上。该字段的目标语义是资源唯一 lookup key，但已有两个确定裂缝：

1. Telegram Sidebar 使用 `sidebar_${messageId}_${index}`，没有 `peerId`，且 `index` 不是稳定媒体身份：cache 路径取消息缓存数组下标，DOM fallback 取当前网格节点下标。下载队列跨聊天存在，而 Telegram message ID 只在单个 peer 内唯一；不同聊天可能碰撞，同一聊天的 cache/DOM 来源切换也可能漂移。
2. Threads DOM 与 SSR 对同一帖子媒体使用不同 ID：DOM 包含 `dom:${position}`，SSR 使用 `mediaPk`。`mergeSsrAndDomResources` 实际已经按 `messageId + index + type` 判断同一媒体，扫描来源切换后 raw ID 仍会变化。

其它现有身份构造已经覆盖当前可达路径：Telegram A 主消息包含 `chatId + messageId + index`，K 主消息包含 `messageFullId + index`，Instagram 使用 media ID 或 entity/position/type fallback，X 使用 tweet/media identity，Vimeo 使用 video/kind/option identity。A Story 的 32-bit URL 指纹只有理论碰撞，没有当前故障证据，本计划不扩大处理。

## 2. 目标

- 当前 document 的下载列表中，同一 canonical `MediaResource.id` 同时最多存在一个 task。
- 单项、批量、页面按钮与 Popup 共享同一排重行为，不在各调用方重复过滤。
- waiting 收到同 ID 新资源时保留 FIFO 位置，并使用最新可执行材料，避免 signed URL 或来源描述过期。
- downloading 收到同 ID 新资源时复用当前执行，不替换已启动任务的材料。
- failed 收到同 ID 新资源时恢复同一 task，使用最新材料重新等待执行，不增加第二行。
- task 被成功、额度拒绝或取消移除后，用户可以再次下载同一资源。
- 修正 Telegram Sidebar 与 Threads 的 canonical ID，使“同资源同 ID、不同资源不同 ID”成为资源模型合同。

## 3. 非目标

- 不修改 Plan 029 的取消、Worker ready、迟到响应或资源释放合同。
- 不做跨刷新、跨标签页或跨浏览器会话排重，不增加时间窗或持久状态。
- 不增加 `dedupeKey`、第二个资源身份、独立 Set、锁、幂等层或后台恢复。
- 不修改后端 6 小时 Credits 扣费去重规则，不新增后端接口。
- 不按 URL 排重；URL 是可刷新执行材料，不是稳定资源身份。
- 不自动重试普通失败。只有用户再次提交同一 failed 资源或点击现有 retry，才恢复任务。
- 不处理没有真实碰撞证据的 A Story 指纹或其它站点身份假设。

## 4. 已确认决策

### 4.1 唯一身份

`MediaResource.id` 继续是唯一资源身份，不新增平行字段。目标合同为：

> 同一用户可识别下载项在 URL、signed token、DOM/SSR 来源和扫描轮次变化时保持同 ID；不同聊天、帖子、媒体位置、类型或下载选项不得共用 ID。

本计划只修正已证实不满足合同的构造：

| 资源 | canonical ID | 取舍 |
| --- | --- | --- |
| Telegram Sidebar | `sidebar:${chatId}:${messageId}:${type}` | chat 隔离不同聊天；cache 与 DOM 都有同一 message/type，不依赖列表位置 |
| Threads | `threads:${shortcode}:${type}:${position}` | DOM 与 SSR 都能取得；与现有 merge 的 message/index/type 身份一致 |

Telegram 主消息、Story、Instagram、X 与 Vimeo 保持现有 ID 构造。本计划不建立 core 对具体站点的识别分支；站点在创建 `MediaResource` 时负责履行 canonical ID 合同。

### 4.2 入队状态矩阵

`DownloadManager.enqueue` 是唯一排重入口，按输入顺序逐项处理：

| 同 ID 现有状态 | 入队结果 | 资源材料 | completion |
| --- | --- | --- | --- |
| 不存在 | 创建新 task 并尾插 | 使用本次资源，同时保存 retry baseline | 新执行轮次 completion |
| `waiting` | 不创建、不移动 | 用本次资源刷新待执行材料与 retry baseline；重建 waiting 展示字段 | 复用当前轮次 completion |
| `downloading` | 不创建、不移动 | 冻结已启动任务材料 | 复用当前轮次 completion |
| `failed` | 同一 task 恢复为 `waiting` 并尾插 | 使用本次资源替换执行材料与 retry baseline | 重建当前轮次 completion |

Plan 029 已在 HEAD `683c2fe7` 删除用户可见 `cancelling` 状态；030 直接以其最终状态集合为实现基线，不添加兼容分支。

同一批输入按上述规则顺序处理：首个资源创建或恢复任务，后续同 ID 项复用它，因此批内和跨 enqueue 不需要两套逻辑。

### 4.3 completion 与 retry

`enqueue` 继续返回与输入一一对应的 `Promise<void>[]`。重复输入可以引用同一个当前轮次 Promise，使 `downloadOne` 和页面 busy 状态等待真实共享任务，而不是因排重立即恢复空闲。

现有 failed task 的 completion 已经 rejected，不能在恢复后继续复用。Manager 抽取一个内部“创建当前执行轮次 completion”的操作：

- 新 task 创建第一轮 completion。
- `retry(taskId)` 和 failed 状态下的 enqueue 共用同一恢复入口，并创建新轮次 completion。
- 旧调用方持有的旧 Promise 保持原失败结果，不被回写。
- 新轮次 Promise 由 Manager 建立内部 rejection observer；Popup/Widget 的 `retry` 只返回 accepted，不消费 completion，失败时不能产生 unhandled rejection。真实失败仍由 Manager 的既有日志与埋点记录。
- waiting/downloading 重复入队只复用当前轮次，不创建 Promise 或 task。

重建当前执行轮次时，只替换同一 `ManagedDownloadTask` 的 `completion`、`resolveCompletion`、`rejectCompletion`、`completionSettled`。Plan 029 已建立的 `cancelled`、`cancellation`、`resolveCancellation` 保留不变，不为 retry 创建第二个取消 gate。

`initialResource` 从 `readonly` 改为可更新的 retry baseline。waiting 收到同 ID 新资源时同时更新当前执行材料与 `initialResource`；failed enqueue 使用本次新资源更新两者后恢复。显式 `retry(taskId)` 没有新资源，使用最近保存的 `initialResource`。三条路径都沿用现有 `retryQuotaExempt` 语义，不再次扣额。

### 4.4 快照、埋点与 RPC

- 新 task 才记录 `DOWNLOAD_CLICK`。被 waiting/downloading 排重的重复提交，以及 failed 恢复，均不重复记录该埋点。
- waiting 资源刷新只在可见 snapshot 字段变化时 publish；仅 URL、document descriptor 等内部执行材料变化不制造 revision。
- taskId 仍标识任务行与执行轮次所属任务；resourceId 继续用于资源展示和进度校验。排重不改进度事件或取消键。
- `downloadBatch` 不返回逐项排重结果；Popup 已通过队列快照取得真实任务状态。
- `ContentDownloadBatchResponse.started` 在全批被排重时并不表示新任务启动。实施时将其重命名为 `accepted`，含义为至少一个请求资源已成功回查并交给 Manager；`count` 表示成功回查的输入资源数，不表示新建 task 数。调用方不保留旧字段兼容分支。

## 5. 复杂度闸门

本计划不新增状态机、持久状态、锁、版本号或幂等层。排重直接复用现有 `downloadList`，线性查找与当前队列规模一致，不增加第二份索引。

failed 恢复需要把 completion 从“首次调用 Promise”统一为“当前执行轮次 Promise”，属于改写现有内部重试流程。必要证据是现有 completion 在首次失败后永久 settled，而用户已确认 failed 再次提交必须恢复同一 task；简单地复用旧 Promise 会让页面按钮立即失败，简单地创建第二 task 又违反唯一资源任务合同。本文已明确该最小代价，仍需用户批准本计划后才可实施。

## 7. 实施阶段

### 7.1 canonical ID

- 修改 Sidebar 三条资源构造路径，使 cache 与 DOM fallback 使用同一 chat/message/type 身份；保留 `index` 作为本轮展示顺序，不再让它参与 identity。
- 修改 Threads DOM、SSR image 与 SSR video 构造，使来源切换不改变同一帖子媒体 ID。
- 更新 `MediaResource.id` 注释为跨来源 canonical lookup key。

验收：同一 chat/message/type 在 cache 与 DOM 中处于不同列表位置时 ID 仍相同；不同 chat 的同 message/type 不碰撞；Threads 同 shortcode/position/type 的 DOM 与 SSR ID 相同，不同位置或类型不同。

### 7.2 唯一入队与重试轮次

- 在 `DownloadManager.enqueue` 按状态矩阵集中排重。
- 抽取 task 当前轮次 completion 的创建与内部观察，统一新 task、显式 retry 和 failed enqueue；重建轮次只替换 `completion`、`resolveCompletion`、`rejectCompletion`、`completionSettled`。
- 保留同一 task 的 `cancelled`、`cancellation`、`resolveCancellation`，不创建第二个取消 gate。
- 将 `initialResource` 改为可更新的 retry baseline；waiting 与 failed 收到新资源时同步刷新执行材料和 `initialResource`，downloading 冻结。
- 保持返回数组与输入一一对应，并删除“重复资源独立 task”的旧测试合同。

验收：同批与跨入口重复资源始终只有一行、一次扣额和一次真实下载；所有调用方等待同一轮次终态。

### 7.3 RPC、文档与交付验证

- 把 `downloadBatch.started` 收敛为 `accepted`，同步通用与 Instagram handler、Popup resource store fixture 及既有 handler 测试。
- 更新共享与站点文档，删除“重复点击独立执行/重复扣额”的现行合同，在 changelog 记录最终行为变化。
- 完成受影响 unit、全量 check、生产 build 与实际启动。

验收：Popup 请求即使全部命中现有任务也正常返回 accepted；真实队列状态只由 snapshot 表达，不新增提示或 UI 状态。

## 8. 最小测试策略

只修改直接覆盖当前可达路径的既有测试：

1. `sidebar-scanner.spec.ts`：同一 chat/message/type 在 cache 与 DOM 的列表位置不同时仍生成相同 ID；同 message/type 在两个 chat 下生成不同 ID。
2. `threads-media.spec.ts`：同 shortcode/position/type 的 DOM 与 SSR 生成相同 ID；不同位置与类型保持不同。
3. `download-queue.spec.ts`：
   - 同批重复与 active/waiting 跨 enqueue 只保留一个 task，并复用同一 completion；
   - waiting 同 ID 新资源刷新 URL、sourceKind、documentId、filename 与 retry baseline，实际执行使用新材料；
   - downloading 同 ID 新资源不替换已启动材料；
   - failed 同 ID 新资源恢复同一 task、尾插、重建 completion，并按新材料执行；
   - 显式 retry 后的重复 enqueue 等待新轮次 completion；重试再次失败不产生 unhandled rejection；
   - task 移除后同 ID 可以创建新 task。
4. `download-many.spec.ts`：把“重复资源重复执行”改为“一次真实下载与一次额度检查”，保留输入 Promise 全部完成。
5. 既有 handler/Popup store/站点测试只同步 canonical ID 与 `accepted/count` 响应，不复制 Manager 排重场景。

不新增跨刷新、哈希碰撞、旧 ID 兼容、并发锁或取消行为测试。Plan 029 已覆盖取消 gate、旧执行迟到结果与新任务隔离；030 只验证资源排重和 completion 执行轮次。

## 9. 验收标准

1. 当前 document 内同一 canonical resource ID 同时最多一个 task。
2. 单项、批量、页面与 Popup 无论调用顺序都命中同一排重入口。
3. waiting 使用最新执行材料但不改变 FIFO 位置；downloading 不被重复提交替换。
4. failed 再次提交恢复同一 task 行，使用最新资源、重建当前轮次 completion，并保持免二次扣额。
5. 同一批中的重复资源只记录一次新任务点击、调用一次额度并执行一次真实下载。
6. 成功、额度拒绝或取消移除后，同资源可以重新创建任务。
7. Telegram Sidebar 不同 chat 不发生 ID 碰撞，cache/DOM 列表位置变化不改变同一媒体 ID；Threads DOM/SSR 来源切换不改变同一媒体 ID。
8. 不新增 dedupe key、持久化、锁、时间窗、依赖、UI 或 i18n。
9. Plan 029 的取消行为与验收不由本计划修改。

## 11. 已知限制

- 排重只覆盖当前 content document 生命周期；刷新页面或打开另一个标签页会创建独立队列。
- 下载完成并从队列移除后再次点击会重新下载，这是明确行为，不保存下载历史。
- A Story 32-bit URL 指纹存在理论碰撞，但当前没有真实故障证据，本计划不增加防护。
