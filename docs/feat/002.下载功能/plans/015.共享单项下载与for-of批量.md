# 015 · 共享单项下载与 for-of 批量

> **部分作废**：本计划成文于多平台时期。Instagram / X / Telegram / Threads 站点与 `website-tgd-pro`、`extension-pro` 已随单平台（Vimeo）转型整体删除，文中这些平台与站点的条目只作历史记录；现行架构以 `../tech-站点适配.md` 与 `../references/index.md` 为准。
## 1. 目标

把所有站点的下载入口收敛为一个单项函数，批量只负责逐项调用它。

```ts
async function downloadOne(resource: MediaResource): Promise<void> {
  if (!(await quotaService.checkAndConsume(1))) return
  await injectedClient.downloadMedia({ source: toDownloadSource(resource) })
}

async function downloadMany(resources: MediaResource[]): Promise<void> {
  for (const resource of resources) {
    try {
      await downloadOne(resource)
    } catch (error) {
      logger.error('[downloadMany] 单项下载失败:', error)
    }
  }
}
```

额度服务超时、网络错误或服务错误继续使用现有 fail-open：记录错误并返回允许下载。后端明确返回额度不足时只跳过当前资源。前面已经下载的资源保持不变，后面的资源继续逐项处理。

## 2. 非目标

- 不去重资源，不阻止重复点击。
- 不做批量级额度检查，不要求批量全部成功。
- 不保存跨刷新下载状态。
- 不自动重试下载。
- 不增加依赖注入或新的后端接口。
- 不改变 Threads/Vimeo 的关闭状态。

## 3. 依赖

- Plan 014：Instagram Popup 当前 tab 直接查询。

## 4. 改动范围

- 新增或重写 `extension/src/core/content/download/download.ts`，导出具体的 `downloadOne` 和 `downloadMany` 单例函数。
- 新增 `extension/src/content/rpc/injectedClient.ts`，只创建并导出一个模块级具体 Injected client；不从站点入口传入 client。
- `downloadOne` 内部固定调用 `checkAndConsume(1)`，通过后执行一个资源的完整下载。
- `downloadMany` 只使用 `for...of`；每项单独 `try/catch`，错误必须打印并继续。
- 修改 content 下载 handler：Popup 仍发送普通 Chrome RPC 和资源 ID，handler 从当前站点资源容器回查完整资源并入队后立即响应；后台继续观察每项 completion。页面入口的 `downloadMany` 仍等待全部终态。
- 修改 Instagram、X、Telegram 主消息和 Telegram sidebar，使页面入口只调用 `downloadOne` 或 `downloadMany`。
- 删除 `DownloadScheduler`、`DownloadQueue`、各站点自己的额度调用、单项/批量分支和 Popup 下载中资源过滤。
- 不保留业务下载状态；按钮如有瞬时反馈也不参与去重、额度或下载控制。
- Telegram sidebar 保留现有批量确认，确认框必须在调用 `downloadMany` 之前；用户取消时不进入循环。
- Instagram 页面与 Popup 不显示任何下载确认。

## 5. 执行步骤

1. 先为 `downloadOne` 写通过、明确不足和额度服务异常三类测试。
2. 为 `downloadMany` 写顺序调用、单项失败继续和重复资源重复执行测试。
3. 建立唯一具体 download client，让 `downloadOne` 直接发起完整 `downloadMedia` 调用。
4. 迁移 Instagram、X、Telegram 页面入口，并让 Popup content handler 回查资源后调用 `downloadMany`。
5. 删除 Scheduler/Queue、批量额度调用、下载中拦截和站点私有下载组合。
6. 保留 Telegram sidebar 确认并验证调用顺序。
7. 运行三个已启用平台的回归测试和 fresh build。

## 6. 验收标准

- [x] 每个下载资源各调用一次 `checkAndConsume(1)`。
- [x] 额度服务异常时仍调用实际下载，并打印可定位错误。
- [x] 明确额度不足只跳过当前资源，循环继续。
- [x] 第二项下载失败时，第三项仍会执行。
- [x] 重复点击同一资源会再次扣除并再次下载。
- [x] Popup 和页面入口不再过滤正在下载的同资源。
- [x] 下载路径中不存在 `DownloadScheduler` 或 `DownloadQueue`；单项直接调用具体 download client。
- [x] Instagram 任意数量下载均无确认框。
- [x] Telegram sidebar 的确认发生在循环之前，取消时额度调用为零。
- [ ] Telegram A/K 主消息、sidebar 和 Popup 仍能得到正确资源并触发下载。
- [x] 页面刷新后无需保留旧下载状态，用户可重新操作。
- [x] 没有新增依赖或依赖注入。

## 8. 失败与回退

- 单项调用抛错时由循环打印并继续，不引入批量错误协调器。
- UI 显示互相覆盖属于允许行为；用户可刷新页面后重新操作。
- Telegram 回归失败时修正调用参数或确认框位置，不复制另一套额度与批量实现。
- 本阶段可整体回退共享函数接线；回退版本仍必须保持额度服务异常时允许下载。
