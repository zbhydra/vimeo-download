## 1. 交付原则

- 一次交付同时完成 Clink 一次性支付和自动续费能力。
- 不发布只支持一种计费模式的中间版本。商品规则由商品域负责；对商品域允许下单且已启用的商品，Clink 可用性只取全局渠道配置与对应商品渠道价的交集。
- 复用现有 OrderService；不新增一套 Clink 订单系统、Webhook 表、支付尝试表或依赖注入。
- Clink 渠道配置未提供 Sandbox Secret Key 时可完成代码和本地签名验证，但不宣称真实首笔支付完成。

## 2. 执行单元

### 2.1 配置与数据合同

- [x] Provider 解析 `environment`、`request_timeout_seconds`、`secret_key`、`webhook_signing_key`，复用现有渠道配置读取与缓存。
- [ ] 在目标数据库的 `config_payment_channel` 写入并启用 `clink` 渠道配置。
- [x] 商品是否支持 Clink 只由现有商品渠道价配置决定；一次性渠道价的 `provider_sku` 可空，自动续费渠道价写 `<productId>:<priceId>`。
- [x] 复用现有 `auto_renew/provider_sku` 透传链路；按用户批准为 `PaymentRequest` 新增 `user_id`，并由 `order_client` 传入登录用户 ID，不修改商品配置 model/service、商品 service 或客户端下单 API 合同。
- [x] Webhook 和历史订单通过非缓存渠道配置构造 Provider；新订单继续使用现有最多 3 分钟的渠道配置缓存。

验收：不启用 `clink` 渠道时，其他渠道配置和下单行为不变；商品域允许下单且商品已启用时，缺少全局 Clink 渠道或对应商品渠道价均不展示、不允许下单，两项配置都启用时 Clink 成为可用渠道。Clink 密钥不进入 Git diff、日志、前端变量或 API 响应。

### 2.2 Clink Provider

- [x] 新增 `ClinkPaymentProvider`，使用现有 `httpx.AsyncClient`，不引入 SDK。
- [x] 从 `config_payment_channel.config_json` 解析完整 Clink 配置；错误中不回显密钥或 Checkout token。
- [x] `create_payment` 按现有 `PaymentRequest.auto_renew` 分支：`false` 发送 `priceDataList`，`true` 解析现有 `provider_sku` 并发送 `productId + priceId`；通用链路不解析 Clink 字段。
- [x] 严格转换项目 6 位精度金额为 Clink 主币种单位，测试捕获实际 HTTP JSON 验证没有倍数错误。
- [x] 解析 `data.sessionId/data.url`，返回 `sessionId/checkoutUrl/payment_url/url`，不在 Session 阶段返回 `channel_order_id`。
- [x] 将 Provider 注册进现有 `PaymentService`，已停止新销售的历史 Clink 订单仍能构造 Provider 验证回调。

验收：Provider 单元测试证明一次性与自动续费两种请求映射和响应解析，测试数据不依赖具体商品类别或商品 ID。

### 2.3 Webhook 与续费映射

- [x] 新增 `POST /api/callback/clink/payment`，按原始 body 验证 SignType、前后 300 秒时间窗和 HMAC-SHA256。
- [x] 只接受 canonical `order.succeeded` / `invoice.paid` envelope，从 `event.data.object` 取业务对象。
- [x] 一次性 `order.succeeded` 用 `merchantReferenceId` 读本地订单，同时比对本地 `payment_data.sessionId`、渠道、金额和币种；Provider 不读取商品快照。
- [x] `type=onetime` 用 `orderId` 作为 `channel_order_no`。
- [x] recurring `order.succeeded` 验签后返回 2xx，但不履约；自动续费统一由 `invoice.paid` 驱动。
- [x] `invoice.paid` 用 `subscriptionId` 查询 Clink Subscription，以返回的 `merchantReference + sessionId` 双重定位首单，再用 `invoiceId` 作为 `channel_order_no`、`orderId` 作为 `transaction_id`。
- [x] 把 Provider 验证结果交给现有 `handle_payment_callback`，不在路由里复制订单更新/履约逻辑。
- [x] 结构/签名/对账失败返回非 2xx；首次或幂等成功返回 2xx。

验收：直接测试有效签名、被篡改 body、错误 SignType、过期时间戳、双引用不一致、金额/币种不一致、recurring Order 不履约、一次性重投和 Invoice 续费重投。

### 2.4 前端渠道与 Checkout URL

- [x] 现有 Checkout 客户端识别 Clink 返回 URL，不建新的支付状态机或商品到渠道白名单。
- [x] 两套入口都读取 `checkoutUrl/payment_url/url`，允许 Sandbox/正式 Clink Checkout HTTPS host，拒绝其他 URL。
- [x] 渠道选择、新窗口打开、订单轮询、关闭和失败状态复用现有组件。
- [x] 同步维护 website-tgd-pro 的共用支付入口，不出现两站点渠道白名单漂移。（**2026-09-20 补注**：`website-tgd-pro/` 已随产品转型整体删除，本步骤无执行对象。）

验收：前端模块测试证明 Clink 官方 URL 可打开、非官方 URL 被拒绝，原页仍以本地订单轮询为支付结果。

### 2.5 Catalog 与运营配置

- [ ] 从用于 Sandbox 自动续费验收的商品配置生成 `clink-catalog.json`，每个注册商品仅使用一种图片来源。
- [ ] 运行官方 catalog validate/plan/import，把 Sandbox `productId/priceId` 写入对应商品的 Clink 渠道价配置。
- [ ] 使用项目 `sql_executor.py` 配置验收所需的 Clink 渠道价；不在业务代码、测试或长期文档中写死可售商品名单。
- [ ] 用 `clink webhook endpoint ensure` 注册公网 HTTPS `order.succeeded,invoice.paid` 端点，并通过 `sql_executor.py` 把返回的签名密钥写入 Clink 渠道配置。
- [ ] 更新 Clink 密钥后不重启进程，确认下一次 Webhook 使用新签名密钥，新订单配置最多 3 分钟后生效。

验收：运营通过商品渠道价控制商品与 Clink 的关联，实际可用性仍按 2.1 的配置交集和商品域校验决定；计费模式由商品域随订单传入，Provider 不识别商品。已创建订单和已建立的 Clink 周期协议不随之后的配置变化。配置缓存最多 3 分钟后生效。

## 3. 不可独立发布的依赖

```text
配置/数据合同
  -> Clink Provider + Webhook
  -> 前端渠道
  -> Catalog + Sandbox 配置
  -> 自动化验证
  -> 真实一次性 + 自动续费首期 + 后续扣款验收
  -> 启用 clink 渠道
```

步骤可分单元实施和验证，但在两种计费模式都通过前，Clink 商品渠道价配置保持禁用，不形成用户可见中间版本。

## 5. 批准闸门

用户批准本计划后才能实施。批准同时确认：

- Clink recurring 的 `productId/priceId` 作为 Provider 私有复合值存入现有 `provider_sku`，不新增字段。
- 不新增 Webhook Inbox/支付尝试表或 Clink 专用 Redis 幂等层；一次性使用 Clink `orderId`，recurring 使用 Clink `invoiceId`，复用现有订单 CAS 和自动续费 Redis 短锁。
- 商品渠道价配置只影响新订单是否可使用 Clink；已创建订单和已生效的 Clink 周期协议不受之后的配置变化影响。
- 退款、争议、用户取消自动续费不在本计划。
