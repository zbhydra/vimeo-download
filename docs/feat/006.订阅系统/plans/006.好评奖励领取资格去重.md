# 006 · 好评奖励领取资格去重

> **部分作废（2026-09-18）**：本计划实施时包含的 **Telegram 身份维度**已随单平台转型整体删除——`users.tg_user_id` 列标记待删、`POST /api/client/subscription/tg-identity/bind` 端点与插件侧 TG 身份采集链路均已移除。**当前实现只有账号与设备两个维度**，现行合同以 `@../tech-好评赠送订阅.md` 为准。
> 下文提到 TG 身份、`tguserid:` 前缀、绑定端点与绑定快照的段落只作为当时的执行记录保留，不再描述现状。

## 目标

把好评赠送的领取事实从账号永久 Counter 扩展为「账号 / 设备」两维度事实表，减少同一人用多个网站账号重复领取 7 天 Unlimited。**(原计划含 TG 身份维度，已作废。)**

## 依赖 plan

无。与 `@../../005.计数器系统/plans/001.Free额度与首日免费.md` 互相独立，可并行；两者共用同一套 uid 构造 helper 与「普通 INSERT + 捕获唯一键冲突」的写入写法。

## 改动范围

1. 新增好评领取事实表，接管账号 Counter 6001 的写入职责。
2. 历史领取数据从 Counter 迁移到新表（迁移脚本幂等，可重复执行）。
3. claim 入口强制 `X-Device-Id`。
4. 新增 TG 身份绑定接口与 `users` 列（绑定只写账号，不参与领取事实的写入）。
5. 两个插件在 TG 页面加载时采集并绑定。
6. 真实测试、隐私政策与商店声明同步。

## 设计要点

- 领取事实落**一张表**，三个作用域各占一行，`uid` 由唯一 helper 构造；判定是一次 `WHERE uid IN (...)`，任一命中即 `already_claimed`。
- 命中时**不写任何记录**；未命中时按本次可用维度插入 1-3 行，**单事务**，要么全成要么全滚。
- **冲突判定用普通 INSERT + 捕获 `IntegrityError`，不得用受影响行数**：MySQL 的 affected-rows 语义受连接上的 `CLIENT_FOUND_ROWS` 影响，一旦 no-op 插入被报成 1 行，代码会把"行已存在"当成"插入成功"，给已领取过的账号再加 7 天。`uid` 是唯一约束，IntegrityError 无歧义。保留"先查三个 uid"的前置读，让常见路径走廉价读而不是异常路径。
- 资格推导是**纯读**，`checkout-configs` 与 `claim` 共用同一来源；`review_reward_claimed_count` 与 `granted` 分支的返回都改为推导口径（恒为 0 或 1）。
- 「事实插入 + 订阅加时」仍是两个独立事务，顺序事实先、订阅后。`006/tech-好评赠送订阅.md` 的失败语义表随之改述（"Counter" → "领取事实行"）；唯一键让该文档 §7「锁过期后仍可能重复加时」的残余风险消失，该免责声明需删除而不是保留。
- **资格推导失败显示为不可领**：`checkout-configs` 的资格判定失败时返回 `review_reward_claimed_count = 1`（入口隐藏）并记日志，不向上抛异常——该接口同时承载商品与渠道配置，不能因资格判定失败而整体失败。选"不可领"而不是"可领"：两者共用同一份数据源，推导失败时 `claim` 也必然失败，显示可领只会让用户白点一次。
- **绑定触发由插件本地快照管理，快照按网站账号记「已绑定」**：TG 页面加载时读快照（`Record<user_id, true>`），当前网站账号已在快照中就跳过，否则采集 TG 身份并调用绑定接口。**快照不比较 `tg_user_id`**：同一账号换绑另一个 TG 身份也只上报一次（服务端本就「已有值不覆盖」，再报一次没有任何效果），而换网站账号后仍会为新账号上报一次。快照只在 HTTP 成功后写入，失败不写、等下次进 TG 页面重试；**不做登出清理**。**不做「每次进 TG 页面无条件上报」**。
- **插件侧失败一律静默**：读取账号槽位拿不到 TG 身份、上报绑定失败、绑定接口返回错误，都只记日志并跳过，不阻断 Telegram 页面、不影响下载、不打断登录。
- 三个维度都是**客户端自证**，只提高门槛、不防恶意用户。
- TG 身份明文存储：Telegram user id 无 `access_hash` 无法取得任何用户信息。

## 表与列

表名 `user_review_reward`，与 `user_first_day` 同形。

| 列 | 类型 | 约束 | 语义 |
| --- | --- | --- | --- |
| `uid` | `VARCHAR(32)`，`collation=utf8mb4_bin` | PK | 由唯一 uid 构造 helper 生成 |
| `ymd` | `INT` | NOT NULL | 领取日的业务时区 `YYYYMMDD`，仅供审计，不参与判定 |
| `value` | `VARCHAR(128)` | NOT NULL | 带前缀原值（`userid:123` / `Device-Id:xxx`），供人工排查、迁移核对与回滚回填，不参与业务查询。**`tguserid:` 前缀已随 TG 维度删除** |

`collation=utf8mb4_bin` 是硬要求：默认 `_ci` 排序规则下 `abc` 与 `ABC` 相等，一旦某个作用域改用混合大小写编码就会让两个不同作用域碰撞，也会掩盖 Python 与 MySQL 侧的哈希大小写漂移。

`value` 必须带前缀，不能只存裸值——账号 id 与设备标识的命名空间必须可区分。它是设备标识在本库中的明文副本，仍按"排查列、不参与查询、不建索引"处理。

## uid 构造 helper

两个作用域的前缀与算法只有一个来源，Python 侧与迁移 SQL 都从它对齐：

```text
sha256("userid:{user_id}").hexdigest()[:32]
sha256("Device-Id:{device_id}").hexdigest()[:32]
```

约束：Python 侧必须用 `hexdigest()`（小写 hex），不得用 base64、`b16encode` 或 `.upper()`；前缀大小写必须与 SQL 完全一致（注意 `Device-Id:` 带大写 D 与 I）。

## 迁移脚本

迁移落在 `backend/scripts/migrations/`，按仓库既有脚本风格命名（参考 `backend/scripts/backfill_paypal_transaction_ids.py`）。

- **只跑主站部署**：好评赠送是主站功能，Extension Pro 是独立部署与独立库，不执行本迁移。
- **可重复执行**：迁移用 `INSERT IGNORE` + 目标表主键收敛，重复执行无副作用，因此不需要"已执行"标记文件。将来若新增带副作用的迁移，再在该目录下引入标记位约定（例如目录内的执行记录文件）。
- 脚本内不自行拼哈希：uid 一律调共用 helper，保证与运行时写入同源。

## 历史数据迁移

```sql
INSERT IGNORE INTO user_review_reward (uid, ymd, value)
SELECT LOWER(SUBSTR(SHA2(CONCAT('userid:', user_id), 256), 1, 32)), 0, CONCAT('userid:', user_id)
FROM counter_user_lifetime WHERE counter_id = 6001 AND value > 0;
```

- `ymd = 0` 表示"迁移行无业务日期"。**不得**为了补日期改用 `CONVERT_TZ`——本仓库有过命名时区表缺失导致 `CONVERT_TZ` 静默返回 NULL 的事故记录。
- 迁移只覆盖 user scope：旧 Counter 本来就是账号维度，设备与 TG 无历史。
- 迁移只读 `counter_user_lifetime`、不删行，因此新旧两版并存是安全的。
- **核对由迁移脚本自己完成：分批按主键查，断言全部命中**。脚本分页读旧表全部 `user_id`，每批用 uid 构造 helper 生成 uid，再查新表：

```sql
SELECT uid FROM user_review_reward WHERE uid IN ('<uid1>', '<uid2>', '<uid3>');
```

每批必须全部命中，脚本最后报告总命中数（`verified_accounts`）。注意该总数是「新表里能查到的 uid 数」，**包含此前已存在的行**——所以重复执行迁移时它仍报出正确总数，而不是 0；脚本另有 `already_present_accounts` / `pending_accounts` 区分本次新插入与早已存在的行。不使用联表、不新增索引（`uid` 是主键）。

- **不用"两侧计数"做判据**：新版期间会有新领取行写入，两个计数本来就不该相等；而"不低于"也证明不了没漏迁（漏 10 个、同时新增 20 个，计数照样通过）。逐项主键命中才是能真正发现漏迁的判据。
- 另需一条固定输入比对，作为 real 测试用例长期保留：对同一个 `userid:1`，Python helper 与 MySQL `LOWER(SUBSTR(SHA2('userid:1', 256), 1, 32))` 必须输出同一字符串，防止 helper 改动后 SQL 侧漂移。
- 不得在新表上按 `value` 做关联或范围筛选（`value` 无索引）。
- 退役留痕：`CounterId.SUBSCRIPTION_REVIEW_REWARD_CLAIMED` **保留注册**（生产 ID 是合同，不得删除或复用），但在注册表注明"已退役、不再读写"。已核验全仓除 `subscription_client.py` 的待改读取点与被改写的 real 测试外没有其他读者，也没有看板或分析依赖它，冻结不会让任何统计静默变旧。

## 回滚

回滚 = **部署回旧代码**，不需要回填、也不需要清表。

- 新表数据对旧代码完全无影响（旧代码只读 `counter_user_lifetime`），原样保留即可。
- 新版期间领取的账号在旧代码下会恢复"可领"状态，最多再领一次 7 天，明确接受——与发布时的时间差同一口径。

如果后续确实需要把新表事实回填 Counter（例如某次回滚后要长期停留在旧版本），回填靠 `value` 的 `userid:` 前缀筛出账号行写入 `counter_user_lifetime`，同样幂等、可重复执行。

## 验收标准

- 账号、设备、TG 身份任一已有记录时，`checkout-configs` 返回不可领，claim 返回 `already_claimed` 且**不新增任何记录**。
- 全新账号首次领取：账号与设备各写一行；账号已绑定 TG 时再写一行 TG 行。
- 同一浏览器第二个账号无法再领；同一 TG 身份在不同网站账号上无法再领。
- 绑定只写账号：重复绑定同一 TG 身份幂等、已有值不覆盖；绑定不产生任何领取事实行。
- claim 缺少 `X-Device-Id` 时被拒绝；判断或写入失败按既有口径整请求失败，不降级为已领取。
- 迁移核对成立：脚本分批按主键查，**旧表源账号全部命中**；固定输入在 Python helper 与 MySQL 两侧输出一致；原已领取账号在新表中可查到，且仍判为不可领。
- 并发领取不会给同一账号加两次时间（唯一键兜底）。
- 不新增第三方依赖、不做跨产品线去重。

## 测试数据约束

领取事实行是**永久行**，且设备与 TG 作用域跨账号——同一个测试文件里两个用例若共用 device id 或 tg id，第二个用例会被第一个永久挡住。因此每个用例必须使用唯一 device id / tg id，清理必须按 uid 删除新表行（既有按 `user_id` 删 `counter_user_lifetime` 的清理逻辑不覆盖它），并沿用唯一 `test_run_id` 约定。E2E 固定账号同理：`backend/scripts/e2e_seed_user.py` 在每轮 smoke 前按 uid 删除该账号与固定设备的领取事实行，再回读确认 `claimed_count_for_display == 0`。

## 已知限制

- 两个维度都是客户端自证：换个未用过的设备标识即可绕过，只提高门槛不防恶意用户。
- 设备 scope 行是**永久的**（比首日维度更硬）：同一浏览器清除站点数据即可重新获得资格，属门槛不是防线。
- 共享浏览器 profile 上第二个账号会永久失去领取资格，清站点数据可自愈。
- 发布与迁移之间的时间差内，尚未迁移的老用户可再领一次；回滚同理。两项均明确接受，不为此引入停活动或回填步骤。

## 风险与恢复

- 迁移只做插入、不删原 Counter 行，可重复执行。
- 回滚按"回滚"一节执行：直接部署回旧代码，新表原样保留，不清理也不回填。
