# 004 · device_not_trusted mark-log 上报

## 目标

当 website 下载工作区调用受设备可信校验保护的接口失败，且失败原因为 `device_not_trusted` 时，前端继续通过现有 mark-log 通道留下可排障记录。用户侧仍只提示刷新页面后重试。

## 依赖

- 产品口径：`@../feat.md`
- 设备可信校验：`@../tech-邮箱登录设备校验.md`
- 前端可观测：`@../../000.架构/tech-可观测与SLS.md`
- website 规范：`@docs/references/specs/spec-website.md`
- 客户端测试规范：`@docs/references/specs/spec-test-client.md`

## 核心方案

复用现有 `recordHomepageMark()` 双写链路，不新增独立 `mark_type`。

1. 后端设备可信校验失败时，`AUTH_PAGE_REFRESH_REQUIRED` 响应继续保持原有用户文案，同时在响应 `data.failure_reason` 写入 `device_not_trusted`、`device_id_invalid`、`device_id_missing` 等内部原因。
2. 前端 `HomepageApiError` 已能读取 `data.failure_reason`；补齐失败原因提取逻辑，让 `web_parse_failed` / `web_download_failed` 的 `mark_msg.reason` 优先使用 `device_not_trusted`。
3. mark-log 接口继续不受设备可信校验保护。`recordHomepageMark()` 先写 SLS，再请求 `/api/client/mark/record`；任一通道失败都不影响用户刷新重试。
4. 不新增 UI 文案，不自动重置 device_id，不自动重试，避免把风控失败做成复杂自恢复流程。

## 备选方案评估

- 新增 `web_device_not_trusted`：不选。会丢失发生在解析还是下载阶段的上下文，还要扩展后端枚举和后台聚合。
- 只写 SLS：不选。排查后台 `mark_logs` 时看不到同一事件，和现有下载工作区 mark-log 口径不一致。
- 复用失败事件并带 `reason=device_not_trusted`：采用。上下文完整，改动集中，符合现有双写设计。

## 改动范围

### backend

1. `backend/src/app/api/device_dependencies.py`
   - `_raise_auth_page_refresh_required()` 增加 `data={"failure_reason": reason}`。
   - 保留现有 `ext_msg`，后端日志仍可定位 operation、device_id、ip、path。

2. 后端测试
   - `backend/tests/test_server/api/test_auth_api.py`
   - `backend/tests/test_server/api/test_media_pre_v2_client.py`
   - 断言 `AUTH_PAGE_REFRESH_REQUIRED` 响应包含 `data.failure_reason == "device_not_trusted"`。

### website

1. `website-shared/src/homepage-runtime/ga4.ts`
   - `extractFailureReason()` 优先读取错误对象的 `failureReason`，再回退 `code` / `name`。

2. 兼容现有 mirror 文件
   - 若构建仍直接使用 `website/src/scripts/homepage/ga4.ts`，同步相同逻辑，或将其改为只消费 shared 入口。

3. 前端测试
   - `website/tests/module-scripts.test.js` 增加模块测试：
     - `HomepageApiError` 带 `data.failure_reason=device_not_trusted` 时，解析失败 mark 的 `reason` 和 `error.message` 都能保留该原因。
     - `recordHomepageMark()` 仍按 SLS → 后端 mark-log 顺序发起请求。

## 验收标准

1. 删除 Redis 可信关系后调用 `parse-pre-v2`，响应仍是 `AUTH_PAGE_REFRESH_REQUIRED`，并带 `data.failure_reason=device_not_trusted`。
2. website 解析失败时会上报 `web_parse_failed`，`mark_msg.reason=device_not_trusted`。
3. 登录后下载授权失败时会上报 `web_download_failed`，`mark_msg.error.code=10015`，并保留 `device_not_trusted` 原因。
4. `/api/client/mark/record` 不被设备可信校验拦截。
5. SLS 与后端 mark-log 任一失败不阻断用户刷新重试。

## 风险与回滚

- 风险：`data.failure_reason` 暴露内部原因。可接受，因为只包含短枚举，不含 IP、token、Cookie、完整 URL。
- 风险：后端 mark-log 请求也失败。可接受，SLS 已先行尝试，用户可刷新重试。
- 回滚：移除 `data.failure_reason` 输出，并让 `extractFailureReason()` 回到按错误码聚合；不影响设备可信校验主流程。
