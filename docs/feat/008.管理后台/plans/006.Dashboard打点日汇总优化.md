# 006 · Dashboard 日汇总优化（2026-09-10）

## 背景与证据

- 生产日志（2026-09-10）：`GET /api/admin/dashboard` 端点总耗时 4558ms，其中 `mark_stats` 阶段 4024ms；`user_summary` 258ms、`daily_registrations` 240ms 不构成瓶颈。
- 根因：`mark_stats` 对 `mark_logs` 做 60 天范围 `GROUP BY (日桶, mark_type)` + `COUNT(DISTINCT device_id)`，而 `mark_time` 无索引。生产 EXPLAIN 实测：`type=index`、`key=idx_mark_type`（全索引扫描）、`rows≈397267`——成本与范围大小无关。
- `mark_time` 范围查询全库仅 `dashboard_service.get_dashboard_data` 一处；`admin_mark_log_service` 只按 `mark_type` / `log_id` 查询。
- `mark_service.record_mark` 不接收客户端 `mark_time`，入库一律服务器当前时间 → 自然日过完即"封闭"；`record_mark` 全库唯一调用方为客户端 API（`api/client/mark_client.py:50`），所有打点均双写 SLS。
- `get_dashboard_data` 有两个消费方：`/api/admin/dashboard`（JSON）与 `/api/system/dashboard`（密码 HTML 页），共用同一响应结构。
- **用户决策（2026-09-10）**：`mark_logs` 只保留 3 个自然日，更久历史依赖 SLS（logstore `tg-download-mark-log`，双写机制见 `000.架构/tech-可观测与SLS.md`）；日志排查页历史缩短可接受。**dashboard 表格（rows）所需的全部数据（含每日注册人数）都进日汇总表**。
  - **2026-09-18 补注**：logstore 已改名为 `vimeo-download-mark-log`（见下「用户可见行为变化」），阿里云侧同名 project / logstore 尚未创建；创建前两端生产打点静默失败，本 plan 依赖的 SLS 历史日志写入不成立。

## 目标 / 非目标

**目标**：dashboard 表格（rows）的读取成本与 `mark_logs` / `users` 体量脱钩，接口总耗时降到几百 ms 内并长期稳定；`mark_logs` 体积恒定有界。

**非目标**：顶部 summary 卡片（total_users / new_users / 昨日同期 / 活跃 24h·7d）维持实时查询——它们是当前状态或滚动窗口口径，不是自然日桶聚合，且 258ms 非瓶颈；不改 API 响应结构与 admin 前端；不做 SLS 侧任何变更。

## 方案（唯一建议方案）

### 1. 新表 `dashboard_daily_summaries`（每 UTC+8 自然日一行 = dashboard 表格一行的完整离线快照）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| id | BigInteger PK autoincrement | 记录 ID |
| ymd | Integer | UTC+8 自然日 YYYYMMDD，**唯一约束** |
| registered_count | BigInteger | 当日注册人数（users，is_del=false，按 created_at 日桶） |
| data_json | MEDIUMTEXT | 当日各打点类型聚合 `{mark_type: {event_count, device_count}}` |
| created_at / updated_at | BigInteger | 毫秒时间戳 |

- 行数 = 自然日数（60 天 ≈ 60 行），读取为小表范围扫描。
- data_json 先例：`google_metric_snapshots` 用 `data_json` 存"已聚合后的展示数据"（`models/google_metric_snapshot_model.py` 文档注释）；新打点类型自动出现在 JSON 中，无需 DDL。

### 2. 新 service `dashboard_daily_summary_service`

- `recompute_recent()`：
  - 聚合窗口起点 = `min(昨日 +8 0点, summary 表当前 max(ymd) 当日 +8 0点)`，再以 `mark_logs 当前 min(mark_time) 所在日 0点` 收紧下界（`max(...)`）。表空（max(ymd) 不存在）时从 `今日 -59 天` 起算。
  - 语义：稳态恒为 `[昨日 0点, now)`（今天 + 昨天两天，重算昨天以覆盖跨天边界最后几秒落库）；首次部署自动补齐 60 天全范围（此时清理尚未运行，源数据完整）；cron 停摆任意时长后，恢复首轮窗口自动扩展到最后一个已汇总日（含部分日）的当日 0 点，部分日整体重算；**但永不重算早于 mark_logs 最旧数据的天**——那天的打点源数据已被清理，重算会把已有正确汇总覆盖为 0，保持旧汇总值即最优已知真相。无 backfill 特例分支。
  - 同一窗口内两条聚合、合成每 ymd 一行：users 按 created_at 日桶 → `registered_count`；mark_logs 按（日桶 × mark_type）→ 打点格子。每行整行覆盖式 upsert（`on_duplicate_key_update`，幂等；先例：`counter_service.add`）。users 表无保留期，窗口内任何一天的数据都完整，不存在"源被清理后重算出 0 覆盖"的问题；但可重建的历史范围同样受上述窗口（含 mark_logs 下界）限制。
- `list_range(start_ymd, end_ymd)`：按 ymd 范围读汇总行。
- spec-mysql §4 例外登记：upsert-only 汇总表（覆盖重算语义，任意的 update/del/info 会破坏合同），同 counter 例外先例。
- 时区：+8 由本模块显式处理（`utils/time.py` 文档明确 admin 看板场景模块内自理；`get_current_ymd` 是 America/New_York，不可复用）。

### 3. 新 cron 任务 `dashboard.daily_summary_maintenance`（interval 600s）

- 注册进 `CRON_TASKS`；调度器把新任务游标初始化为 `now - interval` → **部署后首轮扫描立即执行**。
- 单任务内顺序执行两步，顺序天然正确（先算后删，首次 backfill 不会被清理截断）：
  1. `recompute_recent()`；
  2. **清理**：分批 `DELETE ... WHERE mark_time < 今日 +8 0点 - 2 天 LIMIT N` 循环（spec-mysql §6 批量删走 SQL 层、须分批），保留今天 + 前两个完整自然日共 3 天。首轮删除约 57 天存量（分批全表扫描，预计分钟级，任务超时上限 300s 内；万一超时游标释放、下轮续删），稳态每轮只删约一天增量。
- 任务委托并记录 duration 日志。

### 4. `dashboard_service` 改造

- 删除 `mark_stats` 与 `daily_registrations` 两个实时聚合，rows 全部来自 `list_range`（缺失日期补零；data_json 解析回填打点格子）。
- 顶部 `user_summary` 查询不变；stage 计时变为 `user_summary` / `daily_summary` / `service_total`。

### 5. 不加 `idx_mark_time`

- 清理机制使 `mark_logs` 恒定在 3 个自然日量级（数千行），窗口聚合与清理的全表扫描均为毫秒级；首次部署的一次性 60 天 backfill 全表扫约 4s，在 cron 300s 超时内。
- 边界条件：该简化以「清理正常运行」为前提。若清理持续失败导致表回升到几十万行，cron 耗时上升会体现在 duration 日志中（可观测）；若未来保留期大幅上调，需按 spec-index 重新评估索引。

## 用户可见行为变化

- 「今天」「昨天」的 `registered_count` 与打点单元格最多滞后 10 分钟（cron 间隔；此前 `registered_count` 实时）；更早历史天在任意故障场景下最终一致（源数据保留期内自动补齐）。
- 日志排查页（`web_parse_failed` 排查与单条重试、web 下载日志）只能看到最近 3 个自然日；更久历史走 SLS logstore `vimeo-download-mark-log` 查询。
- 顶部 summary 卡片保持实时，不受影响。
- 以上同时作用于 `/api/admin/dashboard` 与 `/api/system/dashboard`。

## 已否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| registered_count 存入 (ymd, mark_type) 行，用哨兵 mark_type 值 | 日粒度事实寄生在日×类型粒度表里靠 magic value 区分，类型边界含糊 |
| registered_count 独立第二张汇总表 | 注册与打点同窗口同周期聚合，"一日一行"的 1:1 快照是更少概念的表达；两张表是两份 model/service/读路径 |
| (ymd, mark_type) 关系行存打点、registered_count 另加列 | 同表混两种粒度，registered_count 会在当日每个 mark_type 行上重复或需哨兵行 |
| 只加 `idx_mark_time`，不建汇总表 | 每次打开 dashboard 仍对 60 天行做 GROUP BY + DISTINCT，成本随数据增长且每视图重算 |
| 汇总表 + 索引 + 不清理 | 索引只为聚合管道服务，表仍无限增长；既然 SLS 已有全量日志，保留 3 天即可让索引失去必要性 |
| Redis 缓存响应（TTL 10min） | 过期后仍 4s，多一层缓存概念，问题只是搬移 |
| summary(历史) + 请求侧实时查今天 | 多一段合并逻辑且今天查询仍需索引；admin 看板对 10 分钟滞后不敏感，收益不抵概念 |
| 清理为独立 cron 任务 | 需要额外协调"清理不得先于首次 backfill"的顺序；并入同任务顺序执行天然正确，概念更少 |

## 风险

- 部署窗口：schema 同步后、cron 首轮完成前，表格数据短暂为 0（首轮立即触发，秒级窗口）。
- cron 停摆 / 单轮失败：仪表盘读到旧汇总；恢复后窗口按 `max(ymd)` 自动扩展补齐保留期内的缺口，保留期外的天保持旧值，不加补偿机制。
- 清理上线后，summary 表成为 dashboard 60 天历史的唯一在线数据源（SLS 有原始日志但重建需对齐口径，属人工救援手段，不做自动化）。已知限制：summary 表若被清空或回滚旧备份，`registered_count` 与打点格子**同样**只能补齐窗口内（约 3 天）数据——窗口下界由 mark_logs 最旧数据决定，users 虽无清理也无法越过该下界重建更早的天；此为该灾难场景的既定恢复预期，不做分字段覆盖机制。
- 首轮清理删除约 57 天存量，分批执行期间 mark_logs 写入有轻微竞争（分批 LIMIT 缓解，可容忍）。

## 验收标准

1. EXPLAIN：summary 读走 `ymd` 唯一约束范围；cron 聚合与清理查询在稳态小表上全表扫描（预期内，成本有界）。
2. 本地起后端：cron 首轮 backfill 与 `dashboard.daily_summary_maintenance finished` 日志出现；`GET /api/admin/dashboard` 200，`daily_summary` 阶段计时为读表量级。
3. 数据一致：本地插入 users + mark_logs → 调 `recompute_recent()` → dashboard 数字与直查源表聚合对账一致（含 device 去重、registered_count、昨天/今天窗口、重复执行幂等）；真实时序停摆用例：插入源日志 → 跑一次 recompute（形成部分日）→ 再插入当日更晚的源数据 → 模拟停摆后恢复 → 断言该部分日（含尾部，registered_count 与打点格子）对账一致；**清理下界用例**：源数据早于保留期的天在重算时保持旧汇总值不被清零（registered_count 与打点同受窗口下界约束）。
4. 清理：执行后 `mark_logs` 只剩最近 3 个自然日数据；重复执行幂等；分批删除生效（无长事务）。
5. `uv run black` + `ruff check` + `mypy` 通过；`sync_database_schema.py` 已跑（仅新表）。
6. 文档同步：`008.管理后台/tech-Dashboard.md`（机制 + 口径 + 锚点 + 保留策略）、`spec-mysql.md` §4 例外登记、`008.管理后台/changelog.md`。

## 实施阶段（可独立验收）

1. **阶段 1**：新 model（注册进 `models/__init__.py`）+ `dashboard_daily_summary_service` + `mark_service` 增加分批条件删除方法 + 跑 `sync_database_schema`。验收：表存在，`recompute_recent()` 幂等且对账一致（registered_count + 打点格子），清理方法按 3 自然日保留并分批生效。
2. **阶段 2**：cron 任务 `dashboard.daily_summary_maintenance` 注册（recompute → 清理）+ `dashboard_service` 切读汇总表 + 删两处旧聚合代码（无残留）。验收：两消费方正常返回，耗时下降，mark_logs 保留 3 天。
3. **阶段 3**：测试更新（stage 计时断言、60 天用例插入后走真实 recompute 路径）+ 文档同步。验收：测试全绿，文档一致。
